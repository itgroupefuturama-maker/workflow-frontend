    - **Bug rapporté par l'utilisateur après premier test (2026-08-27) et corrigé** : F5/actualisation redirigeait systématiquement vers `/login`. Cause : `redux-persist` réhydrate `isAuthenticated`/`user` de façon **asynchrone**, et rien n'attendait cette réhydratation avant de monter l'app (`main.tsx`) — `ProtectedRoute` lisait donc un état "non connecté" transitoire au tout premier rendu. Corrigé en ajoutant `<PersistGate>` (composant standard `redux-persist/integration/react`) dans `main.tsx`, qui affiche `PageLoader` le temps (très bref) de la réhydratation avant de monter `<App/>`.

    - **Second bug rapporté après le fix `PersistGate`, diagnostiqué avec le backend (2026-08-27)** : F5 toujours en échec, `/auth/refresh` renvoyait `401 "Refresh token manquant"` même juste après un login frais — le cookie `refresh_token` n'apparaissait pas du tout dans le navigateur. Brief envoyé (`BACKEND_PROMPT_REFRESH_TOKEN_COOKIE.md`), réponse reçue (`FRONTEND_PROMPT_REFRESH_TOKEN_COOKIE.md`) : **cause racine = topologie cross-site en dev**, pas un bug de code. Le frontend (`localhost:5173`) et le backend (`http://andry:5050`, voir `.env.local`) sont deux hostnames différents ; en `SameSite=Lax` (config dev, confirmée correcte côté backend, identique sur les 3 cookies), le navigateur pose bien le cookie au login mais ne l'attache **jamais** automatiquement aux requêtes XHR/fetch cross-site suivantes — seulement aux navigations top-level. Aucune combinaison d'attributs de cookie ne peut contourner ça en HTTP simple (`SameSite=None` imposerait `Secure=true`, rejeté par le navigateur sur `http://` non chiffré). **Premier correctif tenté (`.env.local` → `localhost:5050`) invalide** : le backend tourne en réalité sur une **machine distincte**, accédée via Tailscale (`andry` est un hostname Tailscale, pas un alias local) — `localhost:5050` n'écoute rien sur la machine du frontend. Annulé.

**Correctif retenu — proxy Vite dev**, sans toucher au backend ni changer la topologie réseau réelle :
- `vite.config.ts` : bloc `server.proxy` (`/api` → `VITE_API_URL`, `changeOrigin: true`, préfixe `/api` retiré), actif seulement si `VITE_API_PROXY_URL=/api` est défini — lit sa cible via `loadEnv`, aucune valeur hardcodée dans le fichier versionné.
- `src/service/env.ts` : nouvel export `API_PROXY_URL` (= `VITE_API_PROXY_URL` si défini, sinon retombe sur `API_URL` inchangé — donc aucun risque pour la prod, où le proxy Vite dev n'existe pas).
- `src/service/Axios.tsx` : `axiosInstance` et `refreshAccessToken()` utilisent désormais `API_PROXY_URL` au lieu de `API_URL`.
- `.env.local` (non versionné) : `VITE_API_PROXY_URL=/api` ajouté. `.env.example` documenté (commenté, à activer au besoin).
- **Pourquoi ça marche** : le navigateur ne voit plus qu'une requête vers sa propre origine (`localhost:5173/api/...` ou `serveur:5173/api/...`, peu importe le hostname utilisé pour charger le front — `allowedHosts: ['serveur']` déjà en place) ; c'est le serveur Vite dev, côté Node, qui relaie ensuite vers `andry:5050`. Le cookie posé au login et la requête `/auth/refresh` suivante sont alors **same-origin** du point de vue du navigateur → `SameSite=Lax` fonctionne normalement, sans toucher au backend ni exiger HTTPS.
- Sanity-check : `curl -X POST http://localhost:5173/api/auth/login` → réponse `401` du **vrai** backend (pas d'erreur de connexion), confirme que le relais fonctionne.

**Troisième bug rapporté et corrigé (2026-08-27)** : une fois le cookie enfin transmis, `/auth/refresh` renvoyait `403`. Cause : `refreshAccessToken()` (`Axios.tsx`) utilise `axios` "brut", pas `axiosInstance` — il ne passe donc pas par l'intercepteur qui pose `X-CSRF-Token` sur les requêtes mutantes, et `POST /auth/refresh` en est une. **Bug préexistant à ce chantier** (le même code brut était déjà là avant, juste jamais atteint puisque le cookie n'arrivait pas jusque-là — voir bug précédent). Corrigé en posant `X-CSRF-Token` (lu depuis le cookie `csrf_token`) directement sur cet appel.

**Quatrième bug rapporté et corrigé (2026-08-27)** : après un login **frais** (cookies vidés au préalable), seuls `access_token`/`csrf_token` apparaissaient dans le navigateur — `refresh_token` totalement absent, retour au symptôme du 2e bug (`401 "Refresh token manquant"`). Cause : `refresh_token` est posé par le backend avec `Path=/auth` (sur l'URL réelle, sans le préfixe `/api`), mais vu du navigateur (via le proxy) la requête passe par `/api/auth/login` — un chemin qui ne correspond pas à `/auth`, donc le cookie ne pouvait ni être redemandé ni apparaître comme utilisable sur ce chemin. Corrigé en ajoutant `cookiePathRewrite: { '/auth': '/api/auth' }` à la config du proxy (`vite.config.ts`), qui réécrit le `Path` du cookie pour qu'il corresponde à ce que le navigateur voit réellement à travers le proxy.
